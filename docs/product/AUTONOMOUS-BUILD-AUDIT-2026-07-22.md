# Autonomous build audit — what Loc8 needs next

**Audited:** 2026-07-22

**Plain-English conclusion:** Codex does not need another prompt, Claude handoff
or more general GitHub discovery to continue the software work completed in
Phases 1–4. The locally provable product foundation is built, tested, runnable
and recorded. The next honest promotions require real equipment, a real venue,
authority/consent, production-provider choices or competent independent review.
Synthetic work cannot close those gates.

## What was automatically built

| Product path | Working result | Evidence boundary |
|---|---|---|
| Building truth | Strict shared venue package, stable multi-floor semantic graph, validation, lifecycle and four route profiles | Synthetic four-level venue; not a surveyed building |
| Field onboarding | Command Commissioning / Map Builder with floor/object edits, routes, closure checks, local demo and successor drafts | Browser-local and unsigned |
| Operational clients | Guard floor/zone projection and Command map/route consumption use the same venue package | Projection contract; no physical location result |
| Offline site copy | Fail-closed production installer/provider/store interfaces plus a separate browser-local Gateway simulator and version reconciliation | Simulator is not a Gateway, signature or transfer |
| Phone evidence | Explicit-permission Expo 57 Barometer/DeviceMotion/Magnetometer adapter and deterministic multi-floor replay | Adapter tested with fake ports; no phone/background/accuracy evidence |
| Floor-plan registration | Strict source-pixel JSON, control-point similarity fit, residual/bounds gates, immutable receipt, Command preview/apply and Map Builder handoff | Synthetic pixels/control points; no customer plan or survey |

The final measured baseline is 36/36 test suites and 479/479 tests, all
TypeScript, lint, Command production build, Expo Doctor 20/20, dependency audit
zero, Markdown links, Git whitespace and real-browser interaction/responsive/
console QA. The four product decisions are `RDD-020` through `RDD-023`.

## What Codex can still do without asking

- Maintain/fix these contracts, apps, tests, demos and documentation.
- Add deterministic synthetic cases, adversarial validators and replay fixtures.
- Prepare exact protocols, forms, manifests and runbooks for a named physical or
  provider-backed experiment.
- Analyse user-supplied non-sensitive evidence and promote/repeat/stop against a
  frozen gate.
- Keep local branches/main synchronized after verified commits.

None of those actions can honestly manufacture a phone radio result, physical
floor result, customer-plan permission, security review or deployment identity.

## What is genuinely needed from the owner or outside world

### 1. Physical phone/mesh/floor pack

- Three supported phones for the relay gate, ideally at least one iPhone and one
  Android model, chargers/power meters and permission to install development
  builds.
- A supported iOS toolchain. This machine currently has Xcode 16.2, below the
  Expo SDK 57 native iOS requirement already recorded by the R&D audit.
- More working disk before native builds and large raw evidence. Only about
  4.2 GiB is currently available.
- An isolated layout for A↔B↔C relay, then an authorised multi-storey building
  for stair/lift/ramp/same-floor cohorts.

### 2. Building commissioning pack

- A current floor plan the owner/customer is entitled to use.
- Written permission for the site visit and plan processing.
- At least four well-separated physical control points per tested floor,
  measured/reviewed by an appropriate person.
- One field operator to perform the workflow and a second operator to repeat it
  from the instructions.
- Approved handling, storage and deletion rules before any plan image, sensor
  trace or identifiable movement record is retained.

### 3. Production Gateway/connected-service choices

- The target Gateway runtime/hardware and durable store choice (the current
  research recommends a single-site first target and SQLite/WAL-class semantics,
  but target restart/power-loss proof must run on the chosen appliance).
- Production domain, certificates/PKI, operator/device/site identity provider,
  secrets/key custody, backup destination and deployment environment.
- Authority before creating accounts, purchasing infrastructure, deploying,
  contacting customers or processing live site data.

### 4. Independent review and commercial authority

- Independent cryptography/security review before selecting and claiming a real
  signing/protocol provider; the frozen SEC-05 result found no candidate that
  cleared every cross-platform gate.
- Competent privacy/data-protection, fire/egress/accessibility and hardware/
  regulatory review for the claims each discipline owns.
- A named buyer/operator workflow and written pilot boundary before an
  operational exercise or paid deployment.

## Exact handoff when the owner is ready

The minimum useful message is not another broad build prompt. It is one of:

1. **Physical mesh:** “These are the three phone models/OS versions; development
   builds are authorised; this is the isolated layout; run MESH-01 E01.”
2. **Real mapping:** “We have permission to use this plan/building; these are the
   operators/control points; use the approved evidence rules; run MAP-04.”
3. **Native floor:** “These phones/buildings/participants and this storage/
   deletion protocol are approved; run FLOOR-01.”
4. **Gateway/security:** “Use this target appliance/runtime/store, identity/PKI
   provider and review contact; build and test the production repeat without
   deploying it.”

Until one of those packs exists, the correct R&D decision is **HOLD the physical
or production claim**, not build another simulation and call the category done.
