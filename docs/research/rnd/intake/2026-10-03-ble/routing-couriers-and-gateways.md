# Loc8 structured routing, store-carry-forward and gateway intake

Research date: 2026-10-03 (client context). Scope: source inspection and experiment design, no Loc8 product edits, dependency imports or third-party code copying. Eight upstream repositories across nine snapshots and 36 exact files are pinned in `routing-source-receipt.json`; seven snapshots were isolated shallow clones in `/tmp`, two inspected through pinned GitHub raw URLs. Root licences and selected implementation/header files were read, not a comprehensive dependency/legal audit. No upstream firmware, MATLAB or Java test suite was executed in this research pass.

## What changed the recommendation

The existing July catalogue correctly separates public-domain/permissive components from GPL/custom/MPL sources, but current firmware/API details have advanced. MeshCore's current binary channel datagram API is a concrete opaque carrier for a gateway experiment. A May 2026 MIT graph-only MPR reference offers a reproducible structured selection baseline. The April 2026 dual-radio preprint is useful architecture inspiration but explicitly has no activated LoRa firmware or field-tested backbone. Avoid carrying its headline numbers into Loc8 claims.

Loc8's application payload is **25 bytes**, while its existing native frame is **47 raw bytes** (14-byte v1 header, 8-byte sender ID, 25-byte payload), optionally padded to 256 for piggybacking. `MeshFrameCodec.swift` says raw egress is the default and both forms decode. Preserve the 25-byte codec and native frame semantics; this is not SIG Bluetooth Mesh. The legacy native relay is degree-clamped TTL plus randomized jitter/full fanout. Its dedup identity includes sender, origination timestamp, message type and truncated payload hash, excluding TTL. Neither native identity nor timestamps authenticate an operator/site.

## Mapping to Loc8 without format changes

1. **Relay selection simulation:** compare local duplicate suppression first. Later add an independently implemented graph MPR comparator with oracle topology clearly labelled; then degrade freshness, add directed links and node churn. A full graph oracle is an upper-bound fixture, not knowledge available to current phones. Hold dynamic source routing until verified peer identities/two-hop control-plane design exist.
2. **Store-carry-forward simulation:** keep `createdAt`, monotonic `age`, expiry, copy budget and contact history outside the 25-byte payload. Holding does not decrement hop TTL; successful inter-node forwarding does. Decrement lifetime while held and never renew on duplicate receipt or hop change. Model expiry before contact, contact before expiry, reconnection, rejected transfer, buffer eviction and repeat encounters. Transfer acceptance controls budget commitment; retries must not mint copies. Do not infer global freshness from unauthenticated native timestamps. Persistent production courier delivery needs expiry/authentication metadata beyond local first-seen state.
3. **Traffic classes:** do not store-carry current position telemetry as if still live. Coalesce or expire it aggressively. SOS/incident data may remain deliverable longer but must visibly say delayed, with incident-specific acknowledgement/expiry policy; no simulator result establishes safe emergency delivery.
4. **Gateway seam:** tunnel canonical existing native frames; do not rebuild them through an `originate` call that refreshes timestamp/TTL and defeats dedup. Legacy clients continue BLE operation with no long-range hardware requirement. A gateway outer envelope is permitted on the dedicated bearer without changing consumer BLE packet format.

## Concrete dedicated gateway experiment plan

Status: **plan only**. No LoRa radios, physical BLE gateway or deployment have been validated by this intake.

**Lab topology:** BLE cluster A → local gateway A → LoRa companion A → one or two repeaters → companion B → gateway B → BLE cluster B. Start with two gateway hosts and two matched radios, then add repeaters. Use serial/USB to the companion where practical so its BLE transport does not compete with the gateway's phone-facing BLE role. Consumer clients must remain able to exchange BLE frames with no LoRa companion attached.

**Carrier A:** pinned MeshCore binary channel datagram. `CMD_SEND_CHANNEL_DATA` is 0x3E; experimental `data_type` 0xFFFF is documented. Maximum payload is 163 bytes. Receive notification 0x1B reports payload and SNR; send success means accepted by firmware, not end-to-end delivery. Datagrams have no built-in sender or timestamp. Path-length meanings differ on send/receive; the adapter must never interpret inbound metadata as a return route. No public namespace registration or upstream PR is required for a private lab.

**Carrier B:** pinned current LoRaMesher small opaque application payload with distance-vector/TDMA carrier on equivalent supported hardware. Confirm feature/radio/MCU support before selecting boards; do not assume MeshCore nRF52 firmware and LoRaMesher FreeRTOS/ESP32 run unchanged on identical hosts. Match transceiver, antenna, region, power, bandwidth, spreading factor, placement and traffic. Record differing MCU/scheduler as a confounder if unavoidable. Separately compare the preserved legacy ARQ service if acknowledgements/fragmentation are needed; never assume its paper results apply to new TDMA main. Audit the paper-linked LoRaChat licence before using that separate MQTT gateway code; it was not cleared here.

**Outer envelope design for the lab:** protocol version, configured site/shift scope, immutable message fingerprint, ingress gateway/realm, remaining gateway hop budget, expiry/age, the validated raw 47-byte native frame, and authentication produced by a maintained reviewed provider. Stay ≤163 bytes; initially one native frame per datagram, no batching/fragmentation. Define the envelope precisely and add independent encode/decode vectors before radio use. Gateway authentication attests what a gateway observed; it does not authenticate the claimed legacy phone sender. Until consumer identity/security gates are met, use synthetic packets and do not let unverified bridged events trigger operational Command actions.

**Loop/TTL invariants:** preserve native origination timestamp/payload/sender. Maintain canonical message identity across BLE and long-range hops and a bounded cross-bearer dedup cache. Never refresh TTL on egress; retain per-carrier gateway hop budget separately. Do not bridge back to the ingress realm or bridge a previously bridged message again at the same gateway. Failed queue admission keeps the existing budget. Reserve bounded queue/time/airtime capacity for high-priority lab traffic; coalesce positions and reject expired entries. Partition all queues/dedup/scope state by configured site.

**Measurements:** end-to-end unique delivery, p50/p95/p99 age/latency, native and gateway hop counts, BLE TX/GATT work, LoRa on-air milliseconds, queue age/depth/bytes, duplicate rate, rejections by reason, per-radio current, gateway restart recovery and site-scope rejects. Sweep 1/10/60 packets per minute per gateway, sustained telemetry versus SOS bursts, controlled link loss, obstacles and repeater removal. Treat these rates as experimental inputs, not promised capacity. Measure legacy BLE-only performance with gateways off, then on, including locked/background phone states once real devices are available.

**Predeclared decision gates:** byte-for-byte native payload preservation; zero synthetic cross-site acceptance and zero bridge loops; finite queues and lifetime under disconnection/restart; fail-closed malformed envelope/parser cases; ≥baseline BLE-only delivery with lab gateways unavailable; measurable inter-cluster delivery benefit under the tested loss/range conditions. Set acceptable emergency latency and energy targets from the actual product use case before field testing, not from preprint headline values. Carrier adoption waits for complete selected firmware dependency/notices manifest, radio region/duty-cycle configuration from applicable authoritative documentation, current hardware test results and application-authentication design.

**Next production decision:** keep the current BLE protocol and default relay path while local suppression is measured. If its deterministic model and physical multi-phone tests preserve sparse-path delivery and reduce dense traffic, promote only the relay-policy seam behind a reversible feature flag. Prioritise a separate gateway lab over adding source-route bytes. Store-carry-forward remains simulation-only until trustworthy message age, acknowledgement and scope/security contracts exist.
